ThreatRank Architecture

Machine learning risk prediction and prioritisation for vulnerability assessment reports. This page shows the pipeline as it actually stands: which stages run today, which are designed but unbuilt, and which are still open decisions.

Research question
How can heterogeneous VA findings, including findings without CVEs, be normalized, correlated, and prioritized according to exploit likelihood and attack consequence rather than CVSS severity alone? Wording from the Deliverable 1 review, adopted as the question the system answers.

The pipeline

Reports from more than one scanner enter on the left; an ordered remediation list leaves on the right. Every finding is carried through, not only the ones that name a CVE.

Running today — code exists and has produced results Designed, not built Open decision

Why the label was split

The Deliverable 1 design trained one ranking function on CISA KEV membership. KEV is defined per CVE, so a finding without one can never be positive. It is labelled negative by construction, and the model learns that a missing identifier means low risk.

Changes from the first draft

The first architecture drawing laid out the pipeline clearly and its structure carries over into the design above. The revisions below come from two places: the Deliverable 1 review, and measurements taken in the lab since the drawing was made.

What to change, and why
PriorityChangeReason
Blocking Remove KEV from the input features in stage 4. KEV is the training label. A model handed its own answer as an input scores almost perfectly and the result means nothing. This is the one item that invalidates results rather than merely weakening them.
Blocking Show what the model is trained on. Features go in and a risk probability comes out, but no part of the drawing names the label. That omission is what the Deliverable 1 review identified: the label is defined per CVE while a stated contribution is ranking findings that have none.
Blocking Give findings without a CVE a path through the scoring. Stage 6 weights EPSS as one term of the score. For a finding with no CVE that term does not exist. Even under credentials about one finding in six carries no CVE, and on our test host every finding rated 10.0 is in that group.
Blocking Say where the weights w1 to w6 come from. If the team sets them, the project defines a metric and then grades itself against it, which the methodology rules out. If they are learned, the question of which label supervises them returns.
Revise Collapse the three scoring stages into one. Stage 4 produces a risk probability, stage 6 a weighted score, stage 7 a learned ranking. All three order the same findings. Keep whichever one can be defended and drop the others.
Revise Correct the input format. Reports arrive as XML from OpenVAS and JSON from the Nessus API, both already structured. Drawing PDF and DOCX input with entity extraction describes a harder problem than the one we have, and not the one the working code solves.
Revise Add a verification stage. The review asked how false positives are handled, and we have now measured them on a real host. A pipeline with no verification step reads as though the problem has not been noticed.
Revise Distinguish authenticated from unauthenticated input. On one host within one hour the difference was 63 findings against 399. It changes which features exist at all and how much of the report can be trusted.
Revise Name the classification taxonomy. The six categories in stage 3 are not a standard scheme. Using CWE makes the stage defensible and gives the attack graph something it can consume.

Worth keeping

The numbered stages, the legend, the abbreviation key and the output mock-up should all survive into the next version. The output panel in particular shows what the team is actually building better than any box-and-arrow diagram does, including this one.

Open decisions

  • Which input the system assumes. Credentialed scanning removes most false positives and reveals what the network cannot see, but it is not always available in a real engagement. The pipeline currently accepts both and the choice is not yet made.
  • Whether the attack graph can be built. The consequence head depends on it, and the graph engine has not been compiled or tested once. This is the largest single risk in the design.
  • How low-confidence findings are treated. Detection confidence was tested as a way to separate correct findings from incorrect ones and carries no signal on its own: seven correct and seven incorrect findings all sat at the same value.
  • One unresolved contradiction. For CVE-2023-38709 the package changelog places the fix in a version the host already has, while the vendor advisory demands a later one. Deciding between them needs the advisory contents.
